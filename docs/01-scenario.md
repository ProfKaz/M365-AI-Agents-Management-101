# 1. The inventory problem

## Learning objectives

After this exercise, you should be able to explain why names cannot establish purpose or ownership, recognize functional overlap, and support a governance decision with evidence.

## The setup

Five test users each receive four simple agent recipes. All four families use short, synthetic inputs. The display names deliberately provide little context.

| Maker alias | Email drafts | Meeting minutes | Document text | Slide outlines |
|---|---|---|---|---|
| Maker A | Helper | Atlas | Format | Slides |
| Maker B | Nova | Meeting | Pilot | Atlas 2 |
| Maker C | Asistente | Nova 2 | Proyecto X | Ideas |
| Maker D | Helper 2 | Resumen | Helper Pro | Pilot-2 |
| Maker E | Express | Copi | Docs | Apoyo |

The facilitator keeps an accurate inventory even though learners initially see only names. Never remove valid technical ownership to manufacture an orphaned-agent example.

## Discussion

Ask learners which agents appear to do the same work. Reveal their instructions and compare the answers. Different names can hide the same purpose. Similar names can describe different purposes.

Our recipes deliberately create separate agents with overlapping functions. A second kind of duplication also matters: Microsoft documents that publisher/lifecycle records can make the same underlying Copilot Studio agent appear more than once in administration. Establish the underlying identifiers before counting unique agents or deleting an apparent duplicate. [Microsoft documentation](https://learn.microsoft.com/en-us/microsoft-agent-365/admin/manage-copilot-agents-integrated-apps).

## Minimum review questions

What job does it perform? Who answers for its use? Which information and actions can it reach? Who may use it? What evidence supports those answers? When should it be reviewed or retired?

These are governance questions. The inventory supplies some evidence, while business and data owners supply context that the interface cannot decide for them.
